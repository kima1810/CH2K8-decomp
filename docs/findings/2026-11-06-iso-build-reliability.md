# ISO source-build reliability and diagnostics

Tester failures included a missing compiled host executable after downloading source, and difficulties building from the ISO on other development PCs. Importing disc assets and compiling the game are separate operations. The current launcher now explains this explicitly and links to the dated runnable release.

The source builder now discovers Visual Studio C++ tools with vswhere and imports the x64 compiler/Windows SDK environment without requiring a developer prompt. LLVM, CMake and Ninja are resolved from PATH or common/Visual Studio locations, with minimum Clang/CMake versions checked. Interpreter discovery still validates real Python 3.11+ executables and skips Store aliases.

Every source-build invocation creates a log and structured status report before validating its input or prerequisites. Native processes drain stdout and stderr concurrently; successful compiler stderr is not treated as PowerShell failure. On failure, both the output tail and a separate stderr tail are retained with stage, exit code and recovery advice. The GUI reads live status and reports that stage instead of only the child PowerShell error. The source workspace is locked against overlapping builds. SDK installation completeness is checked before reuse. ISO asset storage can be placed on another drive with -InstallDirectory; -CodeOnly and -Jobs 1 provide compiler-only and reduced-memory paths.

An isolated fresh SDK checkout reproduced long-path failures in dependency checkouts. Git long-path handling is now enabled for clone/submodule operations, and rerunning resumed the downloaded dependencies. Native imports also normalize the output/staging root before creating its private directory. The ISO reader retains known-layout fast paths and searches sector-aligned XDVDFS descriptors within a bounded first 1 GiB for other partition placements. Executable hash errors now report observed/expected hashes and distinguish an unsupported revision from legitimacy. No unchecked revision bypass was added: manifest addresses and generated code remain revision-specific.

The isolated build uses tracked source and reviewed build/native-tool changes, excluding unrelated in-progress GPU wait work in the main checkout. Verification covers the retail ISO, SDK download and patching, SDK compilation and game compilation, plus the automated native/launcher/source-build regressions. Generated code, SDK builds and retail disc contents remain private local inputs/outputs; the public repository contains the scripts, configuration, patches, headers and notices needed to reproduce the build with the user's own supported disc.

The clean-build audit also found that an existing CMake cache can keep rexglue_DIR pointing at an older SDK even when CMAKE_PREFIX_PATH is changed. Source builds now pass the selected SDK package directory explicitly, so code generation and host compilation use the same SDK selection.

Final link testing reproduced a mixed-Microsoft-toolset failure (__std_find_first_of_trivial_pos_1 / __std_find_last_of_trivial_pos_1) with VS 2022 and VS 2026 installed together. The old component-ID filter excluded the newer complete toolset while LLVM discovered its STL headers. Toolchain discovery now sorts all installations by version and checks their actual C++ files rather than assuming a component ID. A Windows C++ compile/link/run probe executes before SDK work, and the report records the selected VCTools path. A regression covers old, new and incomplete side-by-side installations.
